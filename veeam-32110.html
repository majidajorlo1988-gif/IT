از قانون کلاسیک 3-2-1 تا Immutable، Offline و Air-Gapped Backup؛ چطور یک معماری Backup مقاوم در برابر Ransomware طراحی کنیم و مطمئن شویم Backup واقعاً قابل بازیابی است؟

چرا 3-2-1 به‌تنهایی کافی نیست؟

قانون 3-2-1 سال‌ها به‌عنوان یکی از اصول مهم Backup مورد استفاده قرار گرفته است. این قانون می‌گوید باید سه کپی از داده داشته باشیم، روی دو نوع Media مختلف نگهداری کنیم و حداقل یک کپی خارج از محل اصلی باشد.

اما تهدیدهای امروزی، مخصوصاً Ransomware و حملات هدفمند به Infrastructure، نشان داده‌اند که حتی داشتن چند نسخه Backup نیز در صورتی که همه آن‌ها از طریق Network یا Credentialهای مشترک قابل دسترسی باشند، می‌تواند ریسک بالایی داشته باشد.

مسئله فقط تعداد Backupها نیست.
باید مطمئن شویم مهاجم نمی‌تواند همه نسخه‌های Backup را هم‌زمان حذف، رمزگذاری یا دستکاری کند.

بخش اول: سه کپی از داده

اولین عدد، 3 است.

منظور از سه کپی این نیست که سه Backup جدا از Production داشته باشیم. در ساده‌ترین برداشت، یک نسخه Production و حداقل دو نسخه دیگر برای حفاظت و Recovery در نظر گرفته می‌شود.

مثال

COPY #1 Production VM │ ├── SQL Server ├── File Server └── Application Server COPY #2 Primary Backup Repository COPY #3 Secondary / Offsite Backup

بخش دوم: دو Media

عدد 2 به استفاده از دو نوع Media یا Storage اشاره دارد.

دلیل این موضوع کاهش وابستگی به یک نوع Storage است. اگر یک Technology یا Storage Type دچار مشکل شود، نسخه دیگری همچنان می‌تواند قابل استفاده باشد.

بسته به طراحی سازمان، Mediaهای مختلفی می‌توانند در معماری Backup مورد استفاده قرار گیرند.

  • Disk Repository
  • Object Storage
  • Tape
  • Cloud Storage
  • سایر Storageهای مناسب با Policy سازمان

بخش سوم: یک نسخه Offsite

Offsite یعنی یک نسخه Backup در محیطی جدا از محل اصلی نگهداری شود.

فرض کنید Production و Repository اصلی هر دو در Server Room یک ساختمان هستند.

در صورت وقوع حادثه‌ای که کل Site را تحت تأثیر قرار دهد، ممکن است هر دو نسخه از بین بروند.

Offsite فقط به معنی «اتاق دیگر» نیست.
هرچه Failure Domain دو Location بیشتر از هم جدا باشد، حفاظت در برابر Disaster بهتر خواهد بود.

بخش چهارم: Offline یا Immutable

این قسمت یکی از مهم‌ترین تفاوت‌های معماری مدرن Backup با Backup سنتی است.

هدف این است که حداقل یک نسخه از Backup به شکلی محافظت شود که مهاجم نتواند به‌سادگی آن را حذف یا تغییر دهد.

Immutable Backup

در یک Storage یا Repository با قابلیت Immutability، Backup برای مدت مشخصی در برابر تغییر یا حذف محافظت می‌شود.

Offline Backup

Offline Backup به نسخه‌ای اشاره دارد که در زمان موردنظر از دسترس معمول Network خارج است.

Air-Gapped Backup

Air Gap به جداسازی منطقی یا فیزیکی Backup از شبکه و مسیرهای دسترسی معمول اشاره دارد.

هدف اصلی:
اگر Attacker به Domain، Server و حتی Backup Infrastructure دسترسی پیدا کرد، نباید بتواند تمام نسخه‌های Recovery را به‌سادگی نابود کند.

Immutable با Read-Only ساده فرق دارد

یکی از اشتباهات رایج این است که هر Storage با Permission محدود را Immutable تصور کنیم.

Read-Only Permission در یک File Share با Immutability یکسان نیست.

در طراحی واقعی باید مشخص شود که مکانیزم Immutability دقیقاً در کدام لایه اجرا می‌شود و چه مدت Backup را محافظت می‌کند.

چرا Ransomware برای Backup خطرناک است؟

Ransomware فقط فایل‌های کاربران را هدف قرار نمی‌دهد. در حملات پیشرفته، Backup Infrastructure نیز می‌تواند هدف قرار گیرد.

اگر مهاجم Credentialهای کافی داشته باشد، ممکن است تلاش کند:

  • Backupها را Delete کند.
  • Repository را Encrypt کند.
  • Backup Configuration را دستکاری کند.
  • Credentialهای مرتبط با Backup را هدف قرار دهد.
  • مسیرهای Recovery را از بین ببرد.
سناریوی خطرناک:
Production + Backup Repository + Backup Management همگی با یک Credential یا در یک Security Domain قابل دسترسی باشند.

Zero Errors یعنی چه؟

عدد صفر در 3-2-1-1-0 به این مفهوم اشاره دارد که نباید صرفاً به موفق بودن Job اکتفا کنیم؛ باید فرآیند Backup و Recovery را Verify کنیم.

یک Backup Job ممکن است با وضعیت Success تمام شود، اما این موضوع به‌تنهایی اثبات نمی‌کند که تمام سناریوهای Recovery به‌درستی کار خواهند کرد.

چه چیزهایی باید بررسی شوند؟

  • وضعیت Backup Job
  • سلامت Repository
  • وجود Restore Point
  • Integrity داده
  • Backup Verification
  • تست Restore
  • بررسی Application Recovery در Workloadهای حساس

Backup Verification با Restore Test

Verification و Restore Test دو مفهوم نزدیک اما یکسان نیستند.

Verification Restore Test
بررسی صحت Backup آزمایش واقعی Recovery
سریع‌تر و قابل تکرارتر شبیه‌سازی سناریوی واقعی‌تر
بررسی Integrity بررسی فرآیند کامل Recovery
جایگزین کامل Restore Test نیست برای Disaster Recovery بسیار ارزشمند است

Security در Veeam فقط به Backup محدود نیست

امنیت Backup Infrastructure باید چندلایه باشد.

Credential Security

حساب‌های مورد استفاده برای Backup باید حداقل سطح دسترسی موردنیاز را داشته باشند.

Network Segmentation

بهتر است Backup Infrastructure بدون نیاز در دسترس تمام سیستم‌های سازمان نباشد.

MFA

در محیط‌هایی که محصول و معماری مورد استفاده پشتیبانی می‌کنند، MFA می‌تواند یک لایه امنیتی مهم برای دسترسی مدیریتی باشد.

Monitoring

Failed Job، Repository Capacity، Unusual Activity و سایر Eventهای مهم باید Monitoring شوند.

Backup Copy چرا مهم است؟

Backup Copy کمک می‌کند یک نسخه دیگر از Backup در محیطی جدا از Repository اصلی داشته باشیم.

این موضوع در طراحی 3-2-1 و معماری‌های چندلایه می‌تواند نقش مهمی داشته باشد.

مثال سازمانی

SITE A Production │ ▼ Veeam │ ▼ Repository A BACKUP COPY │ ▼ SITE B Repository B │ ▼ Immutable Storage

اگر Repository اصلی از بین برود چه می‌شود؟

این سؤال باید قبل از Disaster پاسخ داده شود، نه بعد از آن.

اگر Repository اصلی از بین برود، باید بتوانیم از Copy دوم یا Offsite/Immutable Copy برای Recovery استفاده کنیم.

سؤال طلایی برای هر Backup Administrator:
«اگر همین الان Repository اصلی کاملاً Destroy شود، از کجا Recovery خواهم کرد؟»

چرا RAID Backup نیست؟

RAID می‌تواند Availability و تحمل خرابی Disk را افزایش دهد، اما جای Backup را نمی‌گیرد.

اگر فایل توسط کاربر Delete شود، اگر داده توسط Malware خراب شود یا اگر یک Incident کل Storage را تحت تأثیر قرار دهد، RAID به‌تنهایی راهکار Backup نیست.

RAID = Availability / Storage Resilience
Backup = Data Protection / Recovery

Backup و Disaster Recovery

Backup بخشی از Disaster Recovery Strategy است، اما تمام آن نیست.

یک DR Plan حرفه‌ای باید مشخص کند:

  • چه سرویس‌هایی Critical هستند؟
  • RPO هر سرویس چقدر است؟
  • RTO هر سرویس چقدر است؟
  • Backup از کجا بازیابی می‌شود؟
  • ترتیب Recovery سرویس‌ها چیست؟
  • چه کسی مسئول Recovery است؟
  • چه زمانی آخرین Restore Test انجام شده است؟

چک‌لیست حرفه‌ای 3-2-1-1-0

  • حداقل سه کپی از داده‌های مهم وجود دارد.
  • Backupها فقط روی یک Storage Type نیستند.
  • حداقل یک نسخه Offsite وجود دارد.
  • حداقل یک نسخه Offline یا Immutable در نظر گرفته شده است.
  • Backupها به‌صورت منظم Verify می‌شوند.
  • Restore Test دوره‌ای انجام می‌شود.
  • Repositoryها Monitoring می‌شوند.
  • فضای Storage مرتب بررسی می‌شود.
  • Credentialهای Backup محدود و محافظت‌شده هستند.
  • دسترسی Network به Backup Infrastructure کنترل شده است.
  • Recovery Procedure مستند شده است.
  • سناریوی Ransomware در Recovery Plan دیده شده است.

جمع‌بندی

3-2-1 پایه بسیار خوبی برای طراحی Backup است، اما برای محیط‌های امروزی باید به موضوعاتی مانند Immutability، Isolation، Offsite Storage و Recovery Verification نیز توجه کرد.

مفهوم 3-2-1-1-0 کمک می‌کند نگاه ما از «Backup Job موفق» به سمت یک Recovery Architecture واقعی تغییر کند.

در نهایت، ارزش Backup زمانی مشخص می‌شود که Production دیگر در دسترس نیست و سازمان باید بتواند سرویس‌های حیاتی خود را دوباره راه‌اندازی کند.
