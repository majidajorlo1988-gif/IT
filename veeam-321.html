Veeam 3-2-1 Backup چیست؟ راهنمای طراحی استراتژی Backup

چرا داشتن یک Backup کافی نیست؟ آشنایی با قانون 3-2-1، Repository، Retention، Backup Copy، Offsite Backup و طراحی یک سیستم Backup قابل اعتماد برای زیرساخت‌های سازمانی.

Backup واقعاً یعنی چه؟

Backup یعنی ایجاد یک نسخه قابل بازیابی از داده‌ها، سیستم‌ها یا ماشین‌های مجازی به‌گونه‌ای که در صورت از دست رفتن اطلاعات بتوان آن‌ها را Restore کرد.

بسیاری از سازمان‌ها تصور می‌کنند اگر یک Backup Job با وضعیت Success داشته باشند، کار تمام شده است. اما در طراحی حرفه‌ای Backup، فقط «ساختن Backup» مهم نیست؛ مهم‌تر از آن، امکان بازیابی موفق اطلاعات در زمان نیاز است.

Backup بدون Restore Test، فقط یک فرض است.
تا زمانی که فرآیند بازیابی را آزمایش نکرده‌ایم، نمی‌توانیم با اطمینان بگوییم Backup ما در شرایط Disaster قابل استفاده خواهد بود.

قانون 3-2-1 چیست؟

قانون 3-2-1 یکی از اصول شناخته‌شده در طراحی Backup است. ایده اصلی این است که برای داده‌های مهم، یک نسخه تنها کافی نیست.

3
سه کپی از داده حداقل سه نسخه از داده‌های مهم در نظر گرفته شود.
2
دو نوع Media نسخه‌ها روی حداقل دو نوع Media یا Storage قرار گیرند.
1
یک نسخه Offsite حداقل یک نسخه در محل دیگری نسبت به محیط اصلی نگهداری شود.
اصل مهم:
هدف 3-2-1 این است که خرابی یک Server، Storage، Site یا نوع خاصی از Media باعث از بین رفتن تمام نسخه‌های Backup نشود.

ساختار ساده 3-2-1

Production داده اصلی
→
Backup Repository نسخه Backup
→
Offsite Copy نسخه خارج از Site

در یک طراحی ساده، داده اصلی روی Production قرار دارد، Backup روی Repository داخلی ذخیره می‌شود و یک Copy دیگر به یک Storage یا Site دیگر منتقل می‌شود.

چرا یک Backup Server کافی نیست؟

تصور کنید تمام Virtual Machineهای سازمان روی یک Storage قرار دارند و Backup نیز روی همان Storage یا در همان اتاق نگهداری می‌شود.

اگر یک حادثه جدی مانند خرابی Storage، آتش‌سوزی، سرقت، خرابی برق شدید یا Ransomware اتفاق بیفتد، ممکن است Production و Backup هم‌زمان آسیب ببینند.

Backup باید از Failure Domain اصلی فاصله داشته باشد.
داشتن دو Storage در یک Rack الزاماً به معنی داشتن دو محیط مستقل و امن نیست.

Veeam Backup & Replication

Veeam Backup & Replication یکی از پلتفرم‌های شناخته‌شده برای حفاظت و بازیابی Workloadهای سازمانی است.

در محیط‌های Virtualization، Veeam می‌تواند برای ایجاد Backup از ماشین‌های مجازی، مدیریت Repository، تعریف Retention، اجرای Backup Copy و سناریوهای مختلف Recovery استفاده شود.

در یک زیرساخت معمولی ممکن است اجزای زیر را داشته باشیم:

  • Virtualization Host
  • Virtual Machines
  • Veeam Backup Server
  • Primary Backup Repository
  • Secondary / Offsite Repository
  • Backup Copy Job
  • Monitoring و Alerting

Backup Job چیست؟

Backup Job مشخص می‌کند چه Workloadهایی، در چه زمان‌هایی و با چه تنظیماتی Backup شوند.

مثال

Job Name: Production-VMs-Daily Source: VMware Cluster VMs: DC01 APP01 SQL01 FILE01 Schedule: Daily Retention: Example: 14 Restore Points Target: Primary Backup Repository

مقدار دقیق Retention باید بر اساس نیاز کسب‌وکار، RPO/RTO، ظرفیت Storage و Policy سازمان تعیین شود.

Retention چیست؟

Retention مشخص می‌کند چه تعداد Restore Point یا چه مدت زمانی از Backupها نگهداری شود.

برای مثال، ممکن است سازمان تصمیم بگیرد 14 Restore Point روزانه را نگهداری کند.

Policy نمونه هدف
Daily 14 Restore Point بازیابی روزهای اخیر
Weekly 4 تا 8 Point نگهداری هفتگی
Monthly چند Restore Point نگهداری بلندمدت‌تر
Yearly در صورت نیاز سازمان Compliance / Historical Data

Full و Incremental Backup

یکی از مفاهیم مهم در Backup، تفاوت Full و Incremental است.

Full Backup

در Full Backup یک Backup کامل از داده یا Workload موردنظر ایجاد می‌شود.

Incremental Backup

Incremental Backup تغییرات ایجادشده از Backup قبلی را ذخیره می‌کند. این موضوع می‌تواند مقدار داده‌ای که در هر Backup منتقل و ذخیره می‌شود را کاهش دهد.

نکته:
روش دقیق Backup و Merge/Transform آن به تنظیمات Job، نوع Backup و نسخه محصول وابسته است؛ بنابراین هنگام طراحی باید رفتار واقعی نسخه Veeam مورد استفاده بررسی شود.

Backup Repository چیست؟

Repository محلی است که فایل‌های Backup روی آن ذخیره می‌شوند.

Production
→
Veeam

Repository می‌تواند روی Storageهای مختلف طراحی شود. انتخاب نوع Storage به ظرفیت، Performance، Network، هزینه و نیاز Recovery بستگی دارد.

Backup Copy چیست؟

Backup Copy برای ایجاد یک نسخه دیگر از Backup در یک Repository یا Location دیگر استفاده می‌شود.

این مفهوم برای ساخت لایه دوم حفاظت بسیار مهم است.

Production Source
→
Primary Backup Repository 01
→
Backup Copy Repository 02

Offsite Backup چیست؟

Offsite Backup یعنی حداقل یک نسخه از Backup در Location دیگری نسبت به محیط اصلی نگهداری شود.

این Location می‌تواند یک Server Room دیگر، ساختمان دیگر، Data Center دیگر یا یک محیط Cloud مناسب باشد.

نمونه طراحی دو Site

SITE A Production ↓ Veeam Backup Server ↓ Repository A SITE B Secondary Repository ↑ Backup Copy / Replication

RPO و RTO چه نقشی دارند؟

RPO — Recovery Point Objective

RPO مشخص می‌کند حداکثر چه مقدار Data Loss از نظر زمانی قابل قبول است.

مثلاً اگر RPO برابر یک ساعت باشد، طراحی Backup باید به شکلی باشد که در سناریوی موردنظر بتوانیم حداکثر حدود یک ساعت تغییرات را از دست بدهیم.

RTO — Recovery Time Objective

RTO مشخص می‌کند چه مدت زمانی برای بازگرداندن سرویس قابل قبول است.

مفهوم سؤال اصلی
RPO چقدر Data Loss قابل قبول است؟
RTO چقدر زمان برای Recovery قابل قبول است؟

Backup و Replication یکی نیستند

این دو مفهوم گاهی با یکدیگر اشتباه گرفته می‌شوند.

Backup Replication
برای نگهداری نسخه‌های قابل بازیابی برای ایجاد Replica از Workload
تمرکز بیشتر روی Data Protection تمرکز بیشتر روی Availability / DR
دارای Restore Pointهای مختلف معمولاً Replica نزدیک به Source
برای Recovery از حذف یا خرابی داده بسیار مهم برای سناریوهای سریع‌تر DR مفید
Replication جای Backup را نمی‌گیرد.
اگر داده مخرب یا رمزگذاری‌شده به Replica منتقل شود، داشتن Replica به‌تنهایی لزوماً شما را از Data Corruption یا Ransomware نجات نمی‌دهد.

3-2-1 در برابر Ransomware

یکی از دلایل مهم استفاده از معماری چندلایه Backup، مقابله با سناریوهایی مانند Ransomware است.

اگر Malware بتواند به Production و Repository دسترسی پیدا کند، ممکن است چندین نسخه از اطلاعات تحت تأثیر قرار بگیرند.

به همین دلیل، علاوه بر 3-2-1 کلاسیک، طراحی‌های مدرن‌تر روی Isolation و Immutability نیز تأکید می‌کنند.

اشتباه خطرناک:
اینکه Backup Repository فقط یک Share معمولی باشد و همان Credentialهایی را داشته باشد که Administrator روی Production استفاده می‌کند، سطح ریسک را افزایش می‌دهد.

Immutable Backup چیست؟

Immutable Backup به نسخه‌ای از Backup اشاره دارد که در یک بازه مشخص نمی‌توان آن را به‌سادگی تغییر یا حذف کرد.

Immutability یکی از لایه‌های مهم در طراحی مدرن حفاظت از Backup در برابر حملاتی مانند Ransomware است.

معماری بهتر:
Production → Primary Backup → Offsite / Immutable Backup

سناریوی پیشنهادی برای یک سازمان

Infrastructure

VMware / Hyper-V │ ▼ Veeam Backup & Replication │ ├──► Repository 01 │ └──► Backup Copy │ ▼ Repository 02 │ ▼ Offsite / Immutable

در این معماری، Production تنها نقطه نگهداری داده نیست. چند لایه Backup ایجاد می‌شود تا خرابی یک جزء کل سیستم حفاظت را از بین نبرد.

یک Backup خوب چه ویژگی‌هایی دارد؟

  • Backup به‌صورت منظم و طبق Policy اجرا شود.
  • Jobها Monitoring و Alert داشته باشند.
  • Repository از Production جدا باشد.
  • حداقل یک Copy خارج از Site اصلی وجود داشته باشد.
  • در صورت امکان از Immutability استفاده شود.
  • Restore به‌صورت دوره‌ای آزمایش شود.
  • ظرفیت Repository مرتب بررسی شود.
  • Retention متناسب با Business Requirement تنظیم شود.
  • Credentialهای Backup با Production به‌صورت بی‌دلیل مشترک نباشند.
  • مستندات Recovery در دسترس تیم IT باشد.

اشتباهات رایج در طراحی Backup

  • داشتن فقط یک نسخه Backup
  • نگهداری Backup و Production روی یک Storage
  • نگهداری تمام نسخه‌ها در یک Server Room
  • نداشتن Offsite Copy
  • عدم تست Restore
  • عدم بررسی فضای Repository
  • نادیده گرفتن رشد حجم Backup
  • استفاده از Credentialهای بیش از حد قدرتمند
  • نداشتن Monitoring و Alerting
  • تصور اینکه Replication به‌تنهایی Backup است

محاسبه ظرفیت Repository

یکی از مهم‌ترین قسمت‌های طراحی Backup، تخمین Storage موردنیاز است.

نمی‌توان فقط حجم فعلی VMها را محاسبه کرد و همان مقدار Storage خریداری کرد. باید رشد داده، Retention، Change Rate و ساختار Backup در نظر گرفته شود.

مثال ساده

Production Data: 8 TB Daily Change Rate: 5% Retention: 14 Restore Points Growth: Future expansion required

این اعداد صرفاً یک مثال هستند. ظرفیت واقعی Repository باید با توجه به روش Backup، Compression، Deduplication، Retention و نرخ تغییر واقعی محیط محاسبه شود.

تجربه عملی در محیط Backup

در محیط‌های واقعی، موفق بودن Backup Job تنها یکی از معیارهای سلامت سیستم Backup است.

مواردی مثل پر شدن Repository، قطع ارتباط با Storage، مشکل Permission، خرابی Service، تغییرات شبکه، Credential، Repository Availability و مشکلات مربوط به Virtualization می‌توانند باعث شکست Recovery شوند؛ حتی اگر در ظاهر Configuration اولیه درست باشد.

رویکرد حرفه‌ای:
Backup را به‌عنوان یک سیستم کامل ببینید، نه فقط یک Job. Source، Network، Backup Server، Repository، Storage، Offsite Copy، Monitoring و Recovery Test همگی بخشی از این سیستم هستند.

جمع‌بندی

قانون 3-2-1 یکی از اصول پایه‌ای و ارزشمند در طراحی Backup است: سه کپی از داده، روی دو نوع Media و حداقل یک نسخه خارج از محیط اصلی.

اما در زیرساخت‌های مدرن، طراحی Backup باید فراتر از این عددها باشد و مواردی مانند Offsite Copy، Immutability، امنیت Credential، Monitoring و تست واقعی Restore نیز در نظر گرفته شوند.

در نهایت، هدف Backup این نیست که فقط یک فایل Backup موفق تولید کنیم؛ هدف این است که در روزی که Production از دست رفت، بتوانیم سرویس را با کمترین Data Loss و در زمان قابل قبول برگردانیم.
